# Munkres 算法与角色匹配

## 它解决的是什么问题

高层战术通常写的是：

- 这个角色去接球
- 那个角色去补防
- 另一个角色去盯人

但真正场上跑的是“当前有效的若干台机器人”。  
所以系统需要回答：

> 当前这些任务，应该分配给哪几台真实机器人，整体代价最小？

这就是角色匹配问题。

## 为什么不是简单地“谁近谁上”

如果只有一个任务，最近的人去做通常没问题。  
但一旦是多角色同时匹配，就会出现整体最优和局部最优不一致的问题。

例如两个任务、两台车时：

- 车 1 对任务 A 更近
- 车 2 对任务 B 更近

看上去显然；但在多任务、多角色、带固定编号约束时，必须从 **整体总代价最小** 去分配。

这也是本项目使用 `munkres` 算法的原因。

## 代码里是怎么做的

Python 侧核心在：

- `Algorithm/munkre.py`
- `RoleMatch_LuaStyle/State.py`

思路很直接：

1. 为每个待分配 `Task` 计算一个 `matchPos`
2. 用“机器人当前位置到 `matchPos` 的距离”作为 cost
3. 构造代价矩阵
4. 运行 Munkres，得到任务-车号匹配结果

默认 cost 的定义就是：

```text
cost(task, vehicle) = vehicle 当前坐标 到 task.matchPos 的距离
```

## `matchStr` 是什么

很多 Play 会返回一个字符串，例如：

```text
{LA}(BCD)[EF]
```

它不是随便拼的，而是在描述“哪些角色如何被重新匹配”。

当前约定是：

- `[]`：实时匹配 `RealTime`
- `()`：状态切换时匹配一次 `Once`
- `{}`：Play 切换时才重新匹配，平时尽量保持 `Never`

直觉上可以这样理解：

- 经常变化的角色，用 `[]`
- 希望状态内相对稳定的角色，用 `()`
- 强烈希望保持身份连续的角色，用 `{}`

## 固定车号和自动匹配怎么共存

`Global.py` 里有 `RoleNumberStruct`：

- `Auto`
- `Fixed`

比如守门员 `G` 经常会被固定到某个车号；剩下角色再进行自动匹配。

同时，任务本身也可以指定 `fixedNumber`。  
当前优先级大体是：

- 任务里显式指定的固定编号
- `Global.defaultRoleNumberStructTable` 里的固定规则
- 剩余角色再走 Munkres

## 最容易误解的一点：`matchPos` 不是最终目标点

很多时候 `matchPos` 只是用于“谁更适合拿这个任务”的匹配参考点。  
真实执行时，Skill 里可能还会继续细化：

- 最终站位
- 朝向
- 加速度
- 是否吸球
- 是否避障

所以你应该把 `matchPos` 理解成：

> 用来决定“哪台车来做这件事”最方便的代表位置

而不是“任务最终一定去这个点”。
